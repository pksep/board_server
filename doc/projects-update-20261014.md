# Обновление проектов и комментариев

## Поведение

- Личные списки разделяют созданные и назначенные задачи. Сервер сортирует их по сроку исполнения и выдаёт порциями.
- Состав доски выбирается из действующих участников проекта. Новая доска наследует состав проекта; явно пустой выбор сохраняется.
- Разрешение колонки ограничивает выход задач: любые действия либо только создатель задачи. Это не заменяет проверку доступа к проекту.
- Поля задачи изменяет создатель. Назначенный исполнитель может изменять только дату исполнения. Перемещение сохраняет отдельное правило колонки.
- Задача хранит компактную ссылку на изделие, сборку или деталь. Производственные данные не копируются и не изменяются.
- Лента имеет области «Мои» и «Общие» с постепенной загрузкой. Просмотр самой ленты не снимает счётчик изменений; открытие проекта или задачи снимает соответствующую часть.
- Счётчики комментариев включают корневые сообщения и ответы. Собственные сообщения не являются новыми. Только открытие задачи отмечает её комментарии прочитанными.

## Сохранённые правила

Использованы штатные проверки доступа к проекту и задаче, транзакции перемещения, журнал изменений, ERP-сессия и сервис комментариев. Клиент не выбирает ID читателя. Внешний клиент не может обращаться к внутреннему маршруту счётчиков без сервисного ключа. Удалённые сообщения не учитываются; событие после снимка прочтения остаётся новым.

## Порядок развёртывания

1. Сервис comments: применить миграцию `000006_20261014120000_add-comment-reads.up.sql`, затем обновить сервис.
2. ERP: собрать пакет `packages/zod-shared` штатной командой `bun run build:lib`, собрать и обновить сервер.
3. Board: применить миграции `20261013120000-add-board-members.js`, `20261013130000-add-column-move-permission.js`, `20261014150000-add-task-linked-entity.js`, затем обновить сервер.
4. Обновить клиент после серверных зависимостей.

Для Board, ERP и comments требуется одинаковая переменная `COMMENTS_COUNTERS_KEY`, секрет длиной не менее 32 символов. Передать её через защищённую конфигурацию окружения, не в браузер и не в репозиторий. При отсутствии ключа счётчики возвращают ошибку доступности, а не ложный ноль.

Миграции Board сохраняют старые данные. Откат новых столбцов или таблицы прочтения удалит новые настройки/отметки, поэтому перед откатом необходима резервная копия. Изменение доступа к файловому хранилищу для этого обновления не требуется.

## Проверки

Профильные тесты находятся рядом с сервисами: права полей, перемещение и транзакционный отказ, состав доски, личные списки, лента и счётчики. Проверки клиента дополнительно покрывают состояние разделов, возврат из подзадачи и связанный объект.

Полный доступный набор запускается на итоговом коммите в отдельных локальных базах с одним тестовым процессом. Точные команды, количество успешных/упавших/пропущенных тестов и ограничения полного прогона фиксируются в PR. Старый `src/tests/app.e2e-spec.ts` ссылается на отсутствующие ERP-модули и `test-helper`; этот стартовый сбой нельзя считать успешным прогоном.
