# Выбор сессии Board и Docker-миграции

## Исследованное поведение и основание изменения

ERP-клиент вызывает Board с `credentials: include`; общий перехватчик выполняет
один refresh после 401. SEP Auth выдаёт access-cookie с `COOKIE_DOMAIN`, а refresh
оставляет host-only. ERP пересылает эти cookie через свой канонический auth API.
В документации SEP Auth `.pksep.ru` указан как общий домен ERP и Чата.
Поэтому браузер может отправить на dev и общую production-cookie, и dev-cookie.
Заголовок Cookie не содержит Domain/Path: выбрать нужную сессию по домену после
получения запроса невозможно. `cookie-parser` сохранял только первое значение,
которое также имело приоритет над Bearer. Исправление разрешено требованием
задачи о периодическом 401 при посещении обоих окружений.

## Каноническая проверка

Использованы существующие `TokenAuth`, `AccessTokenService`, `WsGateway`,
SEP Auth `/auth/introspect` и ERP `/auth/check`. Поиск в Board, ERP, SEP Auth,
клиентском Board API и перехватчике refresh не обнаружил готового обработчика
дублирующихся cookie. Новая утилита разбирает только транспорт; проверка
идентичности остаётся в существующем сервисе.

- Явно переданный Bearer — единственный кандидат; отказ проверки не переключает
  запрос на cookie другого пользователя.
- Без Authorization разбираются все одноимённые access-cookie из сырого заголовка,
  одинаковые значения дедуплицируются. Принимается ровно один валидный токен.
- Каждый JWT проверяет authority текущего окружения; заголовок JWT используется
  только для выбора уже существующего central/legacy проверяющего сервиса.
  Подпись, issuer, audience, срок, отзыв сессии и блокировка пользователя сохраняются.
- Ноль действующих токенов или несколько разных действующих токенов дают 401.
  Недоступность authority остаётся 503, а не поводом выбрать другую сессию.
- Синхронизация Board-пользователя происходит только после устранения
  неоднозначности. Выбранный токен используют и следующие ERP-запросы этого HTTP
  запроса. WebSocket хранит его для существующей повторной проверки сессии.
- Legacy Board-режим и его привязка `board_token` к ERP-сессии не меняются.

`AUTH_SERVICE_URL` и `ERP_API_URL` должны указывать на authority своего окружения,
а SEP Auth должен иметь отдельный `ISSUER` для dev и production. Обход проверки
issuer или общая introspection между окружениями недопустимы. Домены cookie этим
изменением не сужаются: это затронуло бы документированный SSO ERP/Чата. На уровне
браузерного транспорта cookie всё ещё могут пересекаться; Board принимает только
сессию своего authority. Для устранения самого пересечения нужны согласованная
карта доменов приложений и миграция cookie на отдельные домены/имена окружений.

## Проверки

`environment-cookies.integration.spec.ts` запускает настоящий Nest guard, HTTP
introspection и проверку RSA JWT. Проверяются оба порядка cookie и оба направления
prod/dev, чужой issuer даже при одном ключе подписи, подпись/audience/expiry,
обновлённый токен рядом со старым, приоритет Bearer, неоднозначность и WebSocket.
Introspection в этом тесте — локальная модель контракта; рабочие dev/prod-сессии
не используются. Ротацию refresh, отзыв и ERP-производственные права этот тест
не подменяет и не заявляет проверенными на dev.

## Миграции Docker

Dockerfile теперь подключает entrypoint. Перед командой приложения запускается
скомпилированный существующий Umzug-мигратор: он применяет pending-миграции и
проверяет, что их больше нет. При ошибке БД, миграции или отсутствии файлов
контейнер завершается ненулевым кодом до старта приложения. Повторный запуск
использует `SequelizeMeta`, конкурентные старты сериализованы advisory lock.
Сами миграции, их транзакции и `down` сохранены. Автоматического пересоздания БД
entrypoint не выполняет. Для новой пустой БД требуется прежняя базовая схема
Board: эти миграции дополняют её и не заменяют начальную установку.

Проверка реального образа на отдельном PostgreSQL:

```sh
docker build --build-arg ENV_FILE=docker.env.example -t board-server:erp872-check .
bun run test:docker:migrations
```

Скрипт создаёт и удаляет только собственные тестовые контейнер/сеть и временные
fixtures. Он проверяет порядок запуска, повторный и конкурентный старт,
сохранение `SequelizeMeta`, отказ при сломанной/отсутствующей миграции. Fixtures
проверяют механизм запуска; бизнес-миграции покрываются существующими отдельными
интеграционными тестами.

Проверка исправления: 99 Jest-тестов в 8 suites прошли; TypeScript
(`tsconfig.build.json`), ESLint изменённых TS-файлов и `git diff --check` прошли.
Docker-образ собран, все описанные проверки запуска на отдельном PostgreSQL
прошли; тестовые контейнер и сеть удалены. Рабочие dev/prod не изменялись.
