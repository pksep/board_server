# Доступ к отчёту времени

До изменения GET `/api/tasks/time-report` требовал авторизацию и доступ к проектам,
а клиент открывал страницу по праву просмотра результатов работ. По запросу
пользователя доступ к странице вынесен в отдельное разрешение роли.

Метод теперь дополнительно проверяет `general.time-tracking:view` и
`general.projects:view` через существующий ERP `/api/authorization/me`.
Используется та же `access_token` cookie, которую проверил общий guard Board.
Токен Board и локальный вход без ERP-сессии не дают доступ к этому отчёту.
Другие cookie не передаются; перенаправления запрещены, ожидание ограничено 5 секундами.

Проверка выполняется для каждого запроса, поэтому отзыв разрешения действует
на следующую страницу отчёта без ожидания устаревшего кеша Board. Ошибка или
неизвестный формат ответа ERP закрывают доступ. Ответ 403 соответствует общему
контракту `PERMISSION_DENIED`, при недоступности проверки возвращается 503.

Права конкретных проектов по-прежнему проверяет `ProjectAccessService` внутри
`TasksService.getTimeReport`. Глобальная роль не позволяет читать чужой проект.
Правила записи времени, диапазон дат, пагинация, авторство и архивирование сохранены.
Общая авторизация других методов не изменена.

Поиск готовой реализации выполнен в Auth, Users и Tasks. Общий guard подтверждает
сессию, но не читает матрицу ролей ERP; справочник Users уже использует безопасный
запрос от текущей сессии. Новый guard подключён только к существующему методу отчёта.
Дублирующий endpoint или отдельная система ролей не создавались.

Порядок обновления: ERP-миграция `20261026090000-time-tracking-permission.js`,
Board, затем клиент. Миграция находится в `sep_erp_server`, ветка `task-controllers`.

Проверки: `time-report-permission.guard.spec.ts` проверяет реальный HTTP-метод
при разрешении, отзыве, отсутствии права и ошибках ERP.
`task-time-report.integration.spec.ts` проверяет записи в отдельной PostgreSQL-базе
и права владельца, участника и постороннего пользователя. В тестах других сценариев
подменяется только новый внешний запрос разрешений, общий guard авторизации сохранён.

## Чтение отчёта через ИИ

Команда task_time_report_get использует тот же TasksService.getTimeReport и TaskTimeReportQueryDto, что страница учёта времени. Отдельных запросов к базе и новых расчётов нет. Перед чтением вызывается общая проверка TimeReportPermissionGuard с текущим делегированным токеном пользователя. ERP разрешает этому токену только GET /api/authorization/me и возвращает актуальные права через AuthorizationService. Результат проверки не кешируется. projects:read сам по себе не заменяет general.time-tracking:view и general.projects:view.

Ответ сохраняет исходных авторов, минуты, комментарии и nextCursor; currentUserId указывает пользователя проверенной сессии, а не исполнителя задачи. Начало периода включительно, конец не включается. Для одного дня используются две соседние полуночи с часовым поясом пользователя. Периоды длиннее 31 календарного дня делятся на соседние части; до полного итога необходимо прочитать все страницы. Производственные отметки читаются существующей командой ERP отдельно.

Порядок выкладки: ERP с разрешённым чтением собственных прав для Board MCP, затем Board, затем AI и добавление task_time_report_get в существующий список разрешённых команд чтения. На старом ERP отчёт завершится отказом проверки доступа. Существующая миграция разрешения страницы обязательна; эта доработка новых миграций не добавляет.

Проверки: projects-mcp-server.service.spec.ts проверяет настоящий протокол MCP, передачу периода/курсора, сохранение автора, отказ scope, отзыв роли и сбой ERP до чтения данных. time-report-permission.guard.spec.ts сохраняет HTTP-сценарии; task-time-report.integration.spec.ts проверяет период, пагинацию и доступ проекта на PostgreSQL. В ERP auth.middleware.spec.ts проверяет точный маршрут, scope, audience, истёкший токен и запрет остальных маршрутов управления правами.
