# ERP-989: task and activity type contracts

## Contract before edits

The user requests continued optimization, correct types in dedicated files, and
no assertion chains hiding type errors. Existing business behavior is fixed.

Search covered task/activity model definitions, controller/service imports,
task time reports, personal/executor tasks, creation/update/attachment flows,
activity writes and their tests. Existing interfaces live in each module's
`interfaces/` directory; move the misplaced declarations there and update every
consumer. Do not keep a duplicate type definition inside a service.

Task relation properties currently use any/any[] even though their association
models are known. Use type-only imports for those model references, retaining
the lazy runtime association resolvers and decorators to avoid circular imports.
Sequelize creation calls currently require casts because Model<T> incorrectly
uses the whole model instance as its creation attributes. Define creation
attributes in the relevant module's interface files and provide Model's second
generic parameter for activity events, assignments, tags and attachments.
Keep the same property objects, defaults, nullability, SQL, persistence methods,
transaction arguments, hooks and afterCommit notifications.

Time/list response shapes, aggregation, cursors, permissions and all rows written
stay unchanged. Type-only imports/declarations must not alter emitted behavior.
No new runtime input validation, error handling, response fields, caching,
database migration or queue behavior is part of this cleanup.

Add compiler checks that reject wrong IDs, missing required creation fields,
unknown association properties and assertion chains. Run application types,
relevant task/activity/time integration tests, unit tests, build and lint.

## Column-filter optimization contract

The canonical column task endpoint uses `findFilterCandidates` followed by
`findFilteredRootTaskIds`; the client supplies creator IDs through the existing
Board API and `TaskListQueryDto` allows up to 100 IDs. Candidate SQL projects only
the fields needed by active filters. Represent that projection with a dedicated
type instead of claiming every candidate is a fully hydrated Task.

For large candidate lists, build one request-local creator-ID Set instead of
linearly scanning up to 100 selected IDs for each task. Preserve Number conversion
of createdById, empty-filter behavior, priority/date AND conditions, association
queries and their options, root-resolution semantics, archive behavior, result
ordering, pagination, access, all writes and notifications. Do not change the
priority predicate, whose lists have only a few elements. Verify full result IDs
against the original helper and measure complete helper calls on identical data.

## Follow-up contract before further edits

Continue the same type cleanup through Project -> Board -> BoardColumn -> Task.
Search covered their models, project create/update/favorite methods and DTOs,
task create/subtask methods, imports/scripts and existing archive/project/activity
integration tests. These use the same canonical ORM methods and lazy association
resolvers. Add only type-only association imports and dedicated creation-attribute
types using actual persisted fields, not model methods/associations. Keep defaults
optional only where database defaults, nullability or existing hooks supply them.
Remove casts from project/member/favorite/task creation while preserving the
exact objects and operation order, validation, hooks, queries, transactions,
afterCommit notifications, history, queue behavior and output ordering.

No conversion of date strings, runtime schema validation or narrowing of allowed
input is included. Task date assignment in update remains a separate issue.

## Earlier results

- Moved five list/time-entry type declarations from TasksService to dedicated
  interface files; all controller/report imports now target those files.
- Typed task relations and related assignment/tag/attachment models using
  type-only imports, keeping the existing lazy runtime resolvers intact.
- Added creation-attribute contracts for events, assignments, tags and
  attachments. Removed nine production `as any`/`as any[]` casts; persistence
  calls, object fields, defaults and transactions stay the same.
- Added a production lint rule rejecting nested assertion chains. Three forms
  (`as any as`, `as unknown as` and angle-bracket chains) were checked against
  the actual ESLint configuration and rejected.
- Added `test:typing` and negative compiler contracts. This check enables
  strictNullChecks: the legacy application's false setting makes Sequelize's
  MakeNullishOptional treat every creation property as optional. The isolated
  strict check rejects missing required fields without changing runtime input
  validation or pretending the entire application is already strict.
- Represented lightweight task filter candidates with a projection type and
  built the creator membership set once per filter request.

Three hundred seeded differential filter scenarios produced identical result
IDs and repository calls, including duplicate IDs, priority/date conditions,
ancestor resolution and association filters. Full-helper synthetic CPU medians:
50 candidates/one creator: 0.0079 → 0.0086 ms (effectively unchanged);
10,000 candidates/100 creators: 2.119 → 1.182 ms. Query parsing, loading and
production endpoint latency are not included in this local CPU benchmark.

Validation passed:

  by seven focused filter/hierarchy tests after the filter optimization.
- 172 PostgreSQL/HTTP integration tests across activity events, task dates,
  Gantt/executor work, time reports, project settings and member ordering.
- Application types, strict type-contract checks, Nest build, changed-file
  ESLint/Prettier and diff checks.

Artifacts: `output/publish-erp-989/board-typing-*.log`,
